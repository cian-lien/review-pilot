## 术语约定

| 术语 | 定义 |
| --- | --- |
| Review Run | 绑定一个 PR、Base/Head SHA 和版本配置的审查执行 |
| Candidate | 尚未通过证据和反证检查的候选问题 |
| Finding | 通过发布门槛、面向维护者展示的具体问题 |
| Evidence | 实际读取到的代码、规则、配置或历史案例引用 |
| Repository Context | 文件、符号、导入、类型和文档等代码上下文 |
| Memory | 可版本化、带来源和适用范围、参与审查的项目知识或偏好 |
| Replay | 固定输入与版本，在历史案例上重新执行审查 |
| Shadow | 使用候选 Memory 进行审查，但不向 GitHub 发布其新增评论 |
| Abstain | 因证据不足、上下文不足或规则冲突而主动放弃评论 |
| Correction | 维护者对 Finding、Memory 或规则范围的显式纠正 |
| Pipeline Version | Prompt、检索、验证、排序与发布策略的不可变版本组合 |

# 第一部分：产品定位与核心闭环

## 1.1 产品定位

ReviewPilot 是一个面向 TypeScript 项目、可纠正、自进化、证据优先的 AI Reviewer。它从真实 PR 与维护者行为中持续学习，维护者始终拥有最终控制权。

对用户的承诺：

1. 给出具体、可行动的问题及其代码证据。
2. 只在足够可信时发布评论，减少审查噪声。
3. 从反馈中调整仓库记忆和审查行为。
4. 让每次自动变化可查看、可纠正、可回滚。
5. 用历史评测与真实反馈验证改进效果。

Repository Context、Memory 和低噪声审查已是同类产品常见能力。ReviewPilot 的差异化假设是把“证据—纠错—进化—评测”做成透明的完整闭环；是否形成真实优势，需要维护者访谈和试用验证。

## 1.2 目标用户与首要任务

首批用户是维护活跃 GitHub 公共 JS/TS 仓库、Review 时间有限、愿意试用自动化工具的维护者。

首要任务是在开发者创建或更新 PR 后，帮助维护者快速找到少数值得处理的问题，并通过反馈减少后续重复误报。

暂不以私有企业仓库、跨语言安全扫描或替代人工批准合并为首要场景。

## 1.3 完整用户闭环

~~~mermaid
flowchart LR
    A["安装 GitHub App"] --> B["启用公共仓库"]
    B --> C["建立代码上下文与初始规则"]
    C --> D["PR 触发审查"]
    D --> E["候选生成与证据验证"]
    E --> F["发布 0–3 条评论"]
    F --> G["Web 查看证据与人工反馈"]
    G --> H["归纳候选 Memory"]
    H --> I["Replay 与 Shadow"]
    I --> J["自动生效或继续观察"]
    J --> D
    J --> K["监控、纠正与回滚"]
    K --> H
~~~

用户可以安装 App、选择仓库、调整范围与预算，在 GitHub 接收简短结果，在 Web 查看证据、纠正结果、管理 Memory 和比较版本。

没有 Finding 是正常成功状态，不应让用户误以为审查失败。

## 1.4 功能边界

P0 是公开 Beta 的必要闭环：

- GitHub 安装、授权与公共仓库管理。
- PR 自动审查、证据验证、摘要与行级评论。
- Web Review 页面、反馈与审查状态。
- 仓库级 Memory、版本、自动验证与人工纠错。
- 后台 Replay、Shadow、激活与回滚。
- 最小权限、租户隔离、成本上限与运行记录。

P1 是可以逐步补齐的体验：

- 完整 Evaluation Lab 页面。
- Patch 生成与预览。
- 多模型对比界面。
- Memory 批量操作与规则导入向导。
- 仓库规则文件同步的完整编辑体验。

Beta 后再建设多语言、复杂调用图、IDE/CLI、GitLab、通用 MCP、多 Agent、自动修复 PR、企业权限与跨仓库知识。

## 1.5 成功目标

初期增长目标为 10 个真实仓库和 100 个真实 PR。评估至少需要实际观察满四周的仓库队列；这些增长与留存目标不能保证在六周开发结束时完成。

- 明确反馈或人工复核的已发布评论有效率达到 70%。
- 每个 PR 默认 0–3 条评论。
- 目标 P90 审查延迟不超过 3 分钟。
- 20 条经系统验证自动生效的 Memory，且可查证生效条件。
- 完成至少 5 次人工纠错后的重新验证与学习案例。
- 四周仓库留存率目标 30%。
- 获得至少 3 位维护者的持续反馈或可公开案例。

若规则数量目标与质量门槛冲突，优先保持质量，不能为了达标批量创建 Memory。

# 第二部分：Review 引擎与证据系统

## 2.1 流水线

~~~text
接收 PR → 固定 SHA 与配置 → 解析变更 → 检索最小上下文
→ 生成候选 → 验证失败路径 → 反证检查 → 去重排序
→ 检查最新 SHA → 发布 → 收集反馈
~~~

采用分阶段、可恢复的流水线。首版可用同一个模型完成不同阶段，但验证阶段应以候选声明和原始证据为输入重新检查，避免仅复述生成结果。

## 2.2 变更理解与首版检查范围

解析新增、修改和删除的函数、组件、接口、类型与配置，比较 Base/Head 行为。优先寻找本次 PR 引入或加剧的问题。

检查方向包括异步错误传播、重复请求与竞态、React 生命周期、服务端与客户端边界、认证授权、运行时数据校验、缓存隔离、数据库事务及仓库业务不变量。

这些是待逐步覆盖的类别，不意味着 MVP 已完整支持所有框架和 ORM。首批专项案例优先覆盖异步/竞态、React 生命周期、输入与权限、Memory 驱动的项目规则。

缺少测试只在能够指出具体新增风险与遗漏验证场景时形成 Finding；不默认对每个变更发布“请补充测试”。

格式、普通命名和注释数量交给现有 Linter，不作为默认 AI 评论内容。

## 2.3 最小充分上下文

每个变更单元按需获取：

~~~text
Diff + 修改前后符号
+ 直接调用与类型关系
+ 相关测试与项目配置
+ 当前生效且匹配范围的 Memory
+ 必要的历史故障背景
~~~

先用路径、Import、符号引用、类型和内容哈希检索，再按需补充语义搜索。MVP 不要求建成完整 Repository Graph 或精确的全仓库调用图。

代码引用绑定文件路径、Commit SHA、行范围和内容哈希。历史 PR 的修复内容只能作为有来源的背景，不能在回放时泄露未来答案。

## 2.4 候选验证与放弃

发布前必须确认：

1. 触发问题的输入、条件或事件序列。
2. 可观察的失败行为与实际影响。
3. 引用代码与行为的因果关系。
4. 问题确由当前 PR 引入或加剧。
5. 已检查相关上游校验、类型约束和适用框架行为。
6. Memory 匹配当前目录、时间和版本。
7. 能提出最小验证方法。

引用缺失、假设无法确认、上下文不全或同级规则冲突时执行 Abstain。静态解析得到的关系只是辅助证据，不能把近似调用关系写成确定的运行时证明。

## 2.5 Finding 示例

~~~json
{
  "id": "finding_123",
  "reviewRunId": "run_123",
  "title": "支付重试生成新的幂等键，可能重复扣款",
  "category": "concurrency",
  "severity": "high",
  "introducedByPR": true,
  "location": {
    "path": "src/checkout/submitOrder.ts",
    "startLine": 81,
    "endLine": 96,
    "commitSha": "固定的 Head SHA"
  },
  "failureScenario": "支付成功但响应丢失后，对同一订单重试会生成新的幂等键。",
  "impact": "支付服务可能将重试视为第二次独立扣款。",
  "evidence": [
    {
      "type": "code",
      "reference": "src/checkout/submitOrder.ts",
      "startLine": 84,
      "endLine": 90,
      "commitSha": "固定的 Head SHA"
    },
    {
      "type": "memory",
      "reference": "PAY-004",
      "version": 3
    }
  ],
  "suggestedVerification": "模拟扣款成功但响应超时，再重试同一订单并检查幂等键。",
  "confidenceScore": 0.93
}
~~~

confidenceScore 在完成校准前是内部排序分，不是“93% 一定正确”。前端应显示可信等级与证据组成，只有校准过的概率才可以百分比形式展示。

## 2.6 去重、排序与发布

- 根因相同的候选合并，即使出现于多个文件。
- 结合代码证据、反证检查、项目规则和历史表现排序。
- 模型自报分数不能单独决定发布。
- 默认每个 PR 最多 3 条；PR 更新时只发布新增根因，避免累计刷屏。
- 低置信内容留在 Web 候选列表，不进入 GitHub 摘要制造额外噪声。
- 行级评论必须绑定有效 Diff 位置；无法锚定但充分可信的问题放入简短摘要。
- 首版默认不自动批准 PR，也不要求 Changes；后者作为显式启用的仓库选项。
- 发布前与发布后核验 SHA；与更新竞态有关的结果标为 Stale，并避免再次发布。
- 只允许应用服务调用 GitHub 写接口，模型输出不具有直接执行权限。

## 2.7 Review Trace

展示读取了哪些文件、命中了哪些 Memory、候选为何被过滤、采用了哪些版本以及最终证据。Trace 记录可审计的输入和决策结果，不展示模型隐藏思维链。

过滤原因包括证据不足、旧问题、上游已有保护、重复根因、范围不匹配、分数不足和规则冲突。

# 第三部分：Web 控制台与关键交互

## 3.1 页面结构

~~~text
ReviewPilot
├── 概览
├── 仓库
│   └── 当前仓库
│       ├── Pull Requests
│       ├── Memory Registry
│       ├── Evaluation Lab
│       ├── 活动记录
│       └── 仓库设置
└── 账户
    ├── GitHub 安装
    ├── 用量与成本
    └── 模型配置
~~~

参考图中的审查、记忆与评测拆成独立页面，通过证据链接互相追溯。顶部保留仓库切换、同步状态、用量和用户菜单。首版界面文案以中文为主，代码、PR 标题、路径与技术名保持原文。

## 3.2 概览与仓库

概览回答最近发现了什么、质量是否改善、哪些事项需处理。

展示启用仓库、近期 Review、高风险问题、近期自动 Memory 变化、延迟、模型成本及需处理的冲突。精度卡片必须附带来源、样本量与反馈覆盖率；样本不足显示“数据不足”。

仓库页展示安装授权、公开状态、同步阶段、最近 PR、当前规则版本和审查开关。仓库变为私有、从安装中移除或卸载 App 时停止首版自动任务。

## 3.3 PR Review

页头展示 PR、分支、Base/Head SHA、Run 版本、覆盖范围和状态。主要页签为发现、已过滤候选、检查、审查记录和已用 Memory。

Finding 列表与证据侧栏并排，显示失败条件、影响、必要代码、验证建议、来源及 GitHub 发布状态。操作包括“有用”“误报”“创建规则”“添加例外”和“打开 GitHub”。

误报原因采用快捷选项：已有校验、符合预期、范围错误、证据错误、非本次引入、其他。默认反馈只影响该 Finding；扩大到文件、目录或整个模式必须由维护者明确选择。

若用户选择长期修正，系统展示预览、来源与适用范围，并提供撤销。单次纠错可以形成负面案例，但不能自动成为全仓库禁报规则。

可选“生成修复”仅提供 Patch 预览、复制或下载，标记“未经运行验证”，不直接改动 GitHub 分支。

## 3.4 Memory Registry

列表显示内容、类型、适用范围、来源、状态、命中数、反馈样本数、最近变化及是否人工锁定。

详情包括支持与反对证据、版本 Diff、关联 Finding、Replay/Shadow 结果和生效记录。操作包括纠正、锁定、暂停、调整范围、添加例外、回滚和退役。

仓库文件规则显示文件路径与可信 Commit，网页只读。首版可生成建议修改内容，供维护者自行提交。

## 3.5 Evaluation Lab

比较 Baseline 与 Candidate 的模型、Prompt、Pipeline、Memory 快照和数据集版本。展示新增发现、减少的误报、新误报、已知问题遗漏及成本变化。

后台评测和门禁是 P0；完整图表和批量操作是 P1。不能因为界面延期而跳过自动学习的验证。

## 3.6 设置

配置自动触发、Draft/Bot PR、目录范围、评论上限、发布可信等级、审查预算、数据保留和自进化模式。

自进化模式：

- Conservative：更长 Shadow 与更严格激活条件。
- Balanced：默认，普通仓库记忆可自动验证与生效。
- Autonomous：缩短低风险 Memory 观察周期，但仍遵守证据、权限和回滚约束。

这些选项只影响仓库 Memory 和审查行为。模型、系统策略与工具权限不会因选择 Autonomous 自动扩大。

## 3.7 状态与异常

Run 状态包括 Queued、Indexing、Reviewing、Verifying、Publishing、Completed、Partial、Stale、Cancelled、Failed。

Completed 可分为有 Finding 与无高可信 Finding。Partial 必须说明实际覆盖了哪些文件、哪些阶段未完成；只发布已经完成验证的子结果。未覆盖范围与“无问题”明确区分。

# 第四部分：系统架构与完整数据流

## 4.1 部署结构

~~~mermaid
flowchart TB
    GH["GitHub App"] --> API["Web / API"]
    UI["Web 控制台"] --> API
    API --> DB[("PostgreSQL")]
    DB --> RW["Review Worker"]
    DB --> EW["Evolution Worker"]
    RW --> GA["GitHub 适配器"]
    RW --> RA["Repository Analyzer"]
    RW --> MG["Model Gateway"]
    EW --> MG
    RW --> AR["审查 Artifact 存储"]
    EW --> AR
    RW --> OB["日志、指标与追踪"]
    EW --> OB
~~~

首版共享领域代码与数据库，以独立进程隔离 Web、长任务和进化任务。PostgreSQL 提供主存储、事务任务和必要的向量检索；大 Artifact 放对象存储。

前端沿用 Next.js/React/TypeScript 的方向。框架、ORM、队列库和模型 SDK 的具体版本在实施计划阶段验证后锁定，不把示例技术栈视为必须安装的全部依赖。

Monorepo 采用 Turborepo；pnpm 负责依赖安装和 workspace，开发、构建、检查、测试、迁移与 Worker 通过 `turbo run` 执行。服务、Worker、迁移、格式化和集成测试不缓存；构建与静态检查使用本地缓存。当前锁定版本及运行方式见 ADR 0001 和 S1 本地接入说明。

## 4.2 模块边界

| 模块 | 职责 | 对外结果 |
| --- | --- | --- |
| domain | 领域类型、状态与不变量 | 验证后的命令和事件 |
| github | 安装授权、读取与发布 | 标准化 GitHub 数据 |
| repository | 固定 SHA 的文件与快照 | 可追溯 Snapshot |
| analyzer | JS/TS 静态与语义关系 | 符号、Import 与近似引用 |
| retrieval | 代码与 Memory 筛选 | 带来源的 Context Bundle |
| review-engine | 候选、验证、去重、排序 | 发布计划与过滤记录 |
| model-gateway | 模型调用、预算与输出校验 | 合法结构化结果 |
| evaluation | Replay、判分与回归比较 | 评测结果与门禁决策 |
| evolution | 反馈归因与 Memory 生命周期 | 新版本、激活或回滚事件 |
| persistence | 数据库、任务、事务 | 可恢复的持久化状态 |
| observability | 指标、日志与 Trace | 可追踪运行记录 |

Web 不直接拼接 Review Prompt，Worker 不直接依赖某家模型 SDK，Memory 文本不能充当可执行脚本。

## 4.3 Webhook 与任务可靠性

~~~text
原始请求体验签
→ 验证事件类型与 Installation
→ 在事务内保存 Delivery 与任务
→ 尽快返回成功
→ Worker 取得租约并异步执行
~~~

Delivery ID 防重投。标准自动审查任务唯一键包含 Installation、Repository、PR、Head SHA 和 Pipeline 版本；Review Run 另外记录 Base SHA、配置和 Memory 快照。

人工重新审查使用明确的 run generation 标识，避免与普通重复事件混淆。Replay 使用独立任务类型，不向 GitHub 发布。

队列按至少一次交付设计，消费者幂等。任务记录租约、重试次数、下一次运行时间、阶段和心跳，崩溃后可恢复。PostgreSQL 事务同时写领域事件和任务，避免双写丢失。

## 4.4 GitHub 集成

使用短期 Installation Token，按仓库范围获取；不持久化长期用户 Token。登录身份不等于仓库管理权限，规则操作需验证当前用户具备对应仓库的维护权限。

计划权限：Contents Read、Pull requests Write、Checks Write、必要 Metadata。普通 PR 对话读取等附加权限按实际端点需求验证后申请，不默认获得代码写入权限。

计划订阅 PR 创建/更新/ready-for-review、Review、Review Comment、Installation 及仓库列表变化。事件与实际权限在实施集成测试中确认。

只有受验证维护者的明确反馈可以作为强纠错信号。外部贡献者的评论是背景数据，不能直接激活规则。

## 4.5 Snapshot 与发布

Snapshot 由固定默认分支或 Base 代码及 Head 增量组成，不每次全仓库重建索引。按内容哈希复用静态索引；每个 Context 片段仍必须绑定当前快照，不能仅用路径命中旧缓存。

Run 创建时冻结 Pipeline、模型配置、预算、仓库规则和 Memory 版本。运行中的学习只影响后续 Run，不改变正在审查的结果。

发布使用本地发布记录、候选指纹和 GitHub 远端 ID。遇到“远端写入成功但响应丢失”，先对账再重试，不能假设数据库唯一键能够使外部 API 恰好执行一次。

## 4.6 核心数据模型

| 实体 | 关键字段与关系 |
| --- | --- |
| users / installations / memberships | 登录身份、安装授权、维护权限 |
| repositories / snapshots | 外部仓库 ID、公开状态、SHA 与索引版本 |
| pull_requests | 仓库与 PR number 唯一，当前 Base/Head |
| review_runs / stages | 固定版本、状态、覆盖范围、阶段 Artifact |
| candidates / findings / evidence | 根因指纹、位置、来源与关联 Run |
| feedback_events | 操作者、权限校验、原始信号、归因与范围 |
| memories / memory_versions / memory_evidence | 当前指针、不可变内容、来源与支持反证 |
| memory_set_versions | 每次 Run 使用的规则版本集合 |
| evaluation_datasets / cases / runs | 数据集版本、标签、固定输入与判分 |
| model_calls / budget_reservations | 模型版本、用途、Token、耗时与费用 |
| webhook_deliveries / jobs | 防重、租约、重试与执行阶段 |
| publication_records / activity_events | 远端发布对账、人工与自动变更 |

重要约束：每个 Finding 属于 Run，至少一条 Evidence；每个核心业务记录包含安装与仓库归属；Memory 修改创建新版本；删除以明确定义的清理流程处理。

## 4.7 故障处理

GitHub 限流按响应提示延后；模型失败进行有限重试或备用模型；备用模型也必须满足门禁。无效 Schema 不进入发布流程。

Worker 恢复阶段 Artifact；PR 更新令旧 Run Stale；权限撤销取消任务；索引失败时只有用户配置允许才进入明确标注的 Diff-only 模式。

大型 PR 按风险和预算划定覆盖范围。超时、超预算或上下文不足不能包装成全量成功。

# 第五部分：自进化 Memory 与人工纠错

## 5.1 自进化的层次

首版自进化包括仓库 Memory、适用范围、候选排序及检索偏好；通过版本化记录、Replay 和 Shadow 自动优化。

不要求在线训练或微调基础模型。自动改写系统 Prompt、自动更换供应商、增加工具权限是平台级变更，需要独立评测和发布策略，不能由某仓库的反馈直接触发。

## 5.2 类型与来源

五类 Memory：

- preference：审查偏好。
- convention：代码约定。
- exception：路径或场景例外。
- invariant：业务不变量。
- failure_pattern：历史失败条件与经验。

文件摘要与普通检索索引属于 Repository Context。

来源支持 Web 手工创建、仓库规则文件、显式规范导入和真实 Review 行为归纳。普通代码惯例只形成候选，不能因为反复出现便认定是必须遵守的规则。

## 5.3 数据与版本

Memory 保存类型、陈述、理由、路径范围、触发条件、严重等级、风险、来源、状态、人工锁定及当前版本。

每个版本不可变，保存作者或模型、Prompt、证据、创建时间、评测、变化原因和前序版本。生命周期变化使用事件记录；回滚移动当前指针并生成事件，不删除历史。

排序分、支持数量与经验有效率分开记录，不用一个数字混合表示。

## 5.4 信号强度与归因

| 信号 | 初始启发式权重 | 使用条件 |
| --- | ---: | --- |
| 明确长期规则指令 | +1.0 | 授权维护者明确范围 |
| 建议 Patch 被采用 | +0.9 | 对齐实际代码修改与根因 |
| 标记有用 | +0.7 | 明确反馈 |
| 按建议修改相关逻辑 | +0.6 | 经归因检查，不仅看代码变化 |
| Thread resolved | +0.3 | 仅弱信号，不作为正确标签 |
| 未回复 | 0 | 保持未知 |
| 当前场景不适用 | -0.5 | 倾向检查 Scope |
| Dismiss | -0.7 | 记录原因未知，不能直接算误报 |
| 明确误报 | -1.0 | 保存纠错证据 |
| 人工规则修订 | 不参与加权覆盖 | 按规则优先级生效 |

这些权重用于排序和候选归纳，不是统计概率。弱行为信号不能单独授权永久例外。

同一 PR 的点赞、解决与采用不能算三个独立证据，应合并为一次观察。多个复制 PR 或自动 Bot 事件同样不能机械累积。

## 5.5 生命周期

~~~mermaid
flowchart LR
    O["Observed"] --> C["Candidate"]
    C --> S["Shadow：通过可用 Replay"]
    S --> A["Active：达到证据与验证条件"]
    A --> Q["Quarantined：明确误报或回归"]
    Q --> C
    A --> R["Retired：人工或验证后退役"]
    A --> N["新版本：强化或人工纠正"]
    N --> S
~~~

Candidate 至少具备规则、范围、来源、反例、风险和验证计划。

初始 Balanced 门槛：

- 3 个来自不同 PR 的独立强支持观察，或一次明确长期指令。
- 内部综合分达到 0.85，仅用作候选门槛。
- 有可用的正例和反例验证，无已知高风险回归。
- Shadow 至少 5 次适用命中。
- 有标签的相关案例预估有效率达到 80%，并满足最低有效样本条件。

最低有效样本条件首版设为至少 10 个有标签的适用案例，且包含至少 3 个不应触发的反例；这是工程筛选门槛，不足以证明统计显著提升。样本不足保持 Shadow，不能用模型的自评分代替。

普通自动规则满足条件后自动 Active，不逐条等待审批。人工明确创建或纠正的低风险规则可以按用户指定范围直接生效，同时异步 Replay 并提示回归。

## 5.6 Replay、Shadow 与冷启动

对比不使用候选 Memory 与使用该 Memory 的结果，固定其他版本。回放只能使用历史 PR 当时可获得的上下文；形成候选规则的案例用于 Development，不能同时充当独立验证证据。

Shadow 运行在之后到达的 PR 上，记录新增问题与过滤变化，但不发布候选规则带来的新增评论。没有维护者反馈的 Shadow 结果不自动成为正确标签，需测试证据、人工标注或明确后续行为支持。

低活跃仓库可能长期停留 Shadow。系统仍能持续观察并改进候选排序，但不能为满足“自进化”宣传缩短证据要求。

## 5.7 自动监控与回滚

- 前 5 次有明确标签的正式命中出现 2 次确认误报：隔离当前自动版本。
- 累计至少 5 次有明确标签命中后，有效率低于 50%：隔离并评估上一版本。
- 明确高风险回归：立即停止该自动版本影响发布。
- 90 天未命中：标记待复核，不等价于规则错误。
- 项目结构变化使 Scope 或符号失效：重新进入 Shadow。
- 只有存在验证合格的前一版本才恢复；没有安全版本则保持暂停。

自动隔离针对自动规则。人工锁定规则不被系统覆盖；发现回归时通知维护者并展示证据。

安全和高影响业务规则可自动提出增强检查，但不能根据负反馈自动生成豁免、取消保护或降低等级。人工拥有明确修改权，操作需记录风险范围和审计事件。

## 5.8 人工纠错与优先级

优先级为：

~~~text
人工锁定规则
> 可信仓库规则文件
> 人工纠正的 Memory
> 自动学习的仓库 Memory
> 平台通用知识
~~~

平台权限和数据处理策略始终位于规则之外，任何仓库规则都不能覆盖。

同级内更精确范围优先，更宽规则保留。真正的同级冲突只暂停受影响规则的自动评论，其他审查继续，并向维护者展示冲突。

纠错流程：记录操作者与范围 → 当前 Finding 标注 → 创建 Memory 新版本或例外 → Replay → 生效、Shadow 或隔离 → Activity 与撤销入口。

“仅本次错误”默认不扩大 Scope；“此目录永不提示”需要用户明确选择。撤销纠错创建新的反向事件，并恢复经验证的规则集合。

## 5.9 仓库规则文件与信任

~~~yaml
version: 1
rules:
  - id: API-008
    type: convention
    statement: "API 错误响应必须包含 requestId"
    severity: high
    include:
      - "packages/api/**/*.ts"
    exclude:
      - "**/*.test.ts"
    locked: true
~~~

文件路径为 .reviewpilot/rules.yml。仅从受信任的已合并默认分支读取规范，并冻结其 Commit。当前外部 PR 对规则文件的修改是待审内容，不能立即作为高优先级规则影响自身审查。

AGENTS.md、CONTRIBUTING.md 和 ADR 的规则导入由维护者选择来源，转成结构化规则并预览。Import 内容本身不具有工具权限；自然语言只能描述审查要求。

网页中的人工锁定与仓库规则冲突必须明确提示，维护者可以修正锁定或通过 PR 更新规则文件。网页不静默覆盖 Git 文件。

## 5.10 跨仓库边界

自动 Memory 默认只作用于当前仓库。其他仓库的业务规则与维护者行为不参与本仓库规则激活。

匿名聚合指标与源代码、原始 Prompt、仓库 Memory 分离。全局样本收集和跨仓库迁移需要独立的用户选择与平台评测，不属于 MVP 默认能力。

# 第六部分：Evaluation Benchmark 与测试策略

## 6.1 四层质量体系

~~~text
确定性测试 → TypeScript Golden 集 → 仓库历史 Replay → Shadow 与真实反馈
~~~

公开 Benchmark 用于可复现回归，历史 Replay 管理特定仓库的变化，线上反馈判断实际价值。

## 6.2 首个 Golden 集

计划整理约 50 个 Case：

| 类型 | 数量 | 目的 |
| --- | ---: | --- |
| 已知真实问题 | 20 | 发现能力 |
| 跨文件问题 | 10 | 上下文价值 |
| 正确但容易误判的 Trap | 15 | 克制与反证 |
| 中性或风格变化 | 5 | 噪声控制 |

Case 绑定仓库 Fixture、Base/Head SHA、依赖与配置版本、输入上下文、预期根因、失败场景、可接受定位、严重等级和禁止误判声明。

真实公共案例与人工构造案例标记区分，保留来源和许可。评测输入不包含 Golden 答案或未来修复。

按 60% / 20% / 20% 分 Development、Validation、Holdout。50 个 Case 的 Holdout 很小，只作初期回归检查；不能宣称其代表全生态精度。不断补充线上失败与新仓库案例，并按仓库和时间控制重复与泄露。

## 6.3 判分

通过文件、SHA、行号和 Evidence 的确定性检查，再判断根因、失败场景及可行动性。

已发布 Finding 分为有效可行动、正确但低价值、误报、待判定。高风险、Judge 不确定以及新增回归需人工复核；LLM Judge 只是辅助匹配，不能自行提供真值。

一个 Golden 根因最多匹配一次。额外重复评论计入噪声。未在 Golden 集中的新问题不直接判错，进入复核补标。

## 6.4 指标口径

| 指标 | 首版定义 |
| --- | --- |
| 已判定发布精度 | TP / (TP + FP)，未知标签不进分母，同时展示覆盖率 |
| 反馈覆盖率 | 有明确判定的评论 / 全部已发布评论 |
| Known-issue recall | 捕获的 Golden 根因 / 全部 Golden 根因 |
| Critical recall | 捕获的高风险 Golden 根因 / 全部高风险根因 |
| Noise per PR | 已确认误报数量 / 已审查 PR 数量 |
| Trap false-positive rate | 出现误报的 Trap Case / 全部 Trap Case |
| Evidence validity | 有效且支持声明的引用 / 经过检查的引用 |
| Duplicate rate | 重复根因评论 / 全部发布评论 |
| 审查稳定性 | 固定版本多次运行的根因集合一致性 |
| Memory lift | 固定其他变量后，Memory 带来的精度与召回变化 |
| 延迟 | 队列等待与执行时间分开，另报用户感知总时长 |
| 成本 | 推理、重试、备用模型、验证与进化成本分别记录 |

之前讨论中的 Precision@3 在首版定义为“最多三条发布策略下的聚合发布精度”，不把零评论 Run 计作完美精度。正式展示使用“发布精度（上限 3 条）”，避免传统 Precision@k 的分母歧义。

F0.5 作为辅助综合指标；发布精度必须同时满足召回与覆盖要求。空输出显示无可用精度，不能靠全部 Abstain 达标。

线上未回复、仅关闭线程与未采用均保持未知。Estimated Precision 必须区分行为推断、明确反馈和人工复核。

## 6.5 初始验收与门禁

| 项目 | 初始目标与门槛 |
| --- | --- |
| Golden 发布精度 | ≥ 75%，展示样本量和置信区间 |
| 真实有效率 | Beta 目标 ≥ 70%，注明反馈覆盖率 |
| 引用有效率 | ≥ 95% |
| 发布位置结构校验 | 100% |
| 高风险已知回归 | 0 |
| 重复评论比例 | ≤ 3% |
| 默认评论上限 | 每个 PR ≤ 3 |
| P90 用户感知延迟 | 目标 ≤ 3 分钟，限定支持的 PR 规模 |
| 平均 Review 模型成本 | 目标 ≤ ¥3 / PR |
| P95 Review 模型成本 | 目标 ≤ ¥8 / PR |

首版固定核心高风险回归集，要求至少捕获其中的确定缺陷；不能以不发布任何内容满足精度门禁。通用召回门槛在首次基线评测后按同一冻结数据集设定，候选版本不得引入核心高风险遗漏。

对模型或 Prompt 等全局版本变更，比较相同数据集、上下文和预算；记录多次运行差异。小样本“提升 2%”不视作确定进步，适用时按 PR 分组计算不确定范围。

## 6.6 Memory A/B 与渐进发布

Control 为原规则集合，Treatment 只增加或修改候选 Memory。要求找到至少一个真实改善、无高风险回归、新增误报在门槛内、成本不过界。

通过后先 Shadow，再按相关路径逐步扩大影响。自动规则不能改变工具权限、全局模型或未授权路径。记录规则版本、数据集和回滚点。

## 6.7 工程测试

确定性单元测试覆盖 Scope、优先级、生命周期、预算和根因去重。

集成测试覆盖 Webhook、事务任务、授权、Snapshot、Structured Output 校验、发布对账及删除。

端到端测试仓库完成安装 → PR → 审查 → 反馈 → Memory → Replay → 激活/回滚。

故障注入必须覆盖重复事件、乱序更新、429、模型超时、无效 JSON、Worker 崩溃、租约竞争、PR 更新、权限撤销、发布响应丢失及预算并发超支。

安全测试覆盖跨仓库引用、恶意规则修改、路径穿越、Prompt Injection、未授权纠错和数据删除后的备份恢复。

# 第七部分：安全、隐私与成本控制

## 7.1 执行与权限边界

MVP 只进行静态读取与解析，不执行 PR 的安装脚本、测试、服务或原生扩展。验证建议与生成 Patch 不表示已经运行验证。

分析器自身也要限制文件大小、文件数、解析深度、CPU、内存与超时；拒绝越界路径和指向仓库外的符号链接。

若未来增加运行测试，使用无凭证、默认无网络、限资源的隔离环境，并单独设计授权与结果验证。

## 7.2 Prompt Injection

代码、注释、文件名、README、PR 描述和普通讨论均为不可信数据。可信规则经过来源验证，但依旧只能描述审查要求。

文本分层只是防线之一，实际安全依赖代码层的读取范围、工具允许列表、Schema、SHA、Scope 与 Evidence 校验。模型不能获得 GitHub Token 或直接调用写操作。

模型输出、规则提案和反馈解释均不得绕过确定性检查。外部 PR 中修改规则不能影响本次评测标准。

## 7.3 身份与租户隔离

每次访问先验证用户权限，再验证安装和仓库归属。UUID 不作为授权依据。

公共 Review 结果可以按产品规则公开，但 Memory 管理、模型配置、审计记录和含敏感内容的 Artifact 需维护者权限。

上下文构建、检索、缓存与 Artifact 下载都检查归属。跨仓库业务 Evidence 导致 Run 失败，并记录异常。平台通用知识单独标记来源，不混作其他用户仓库证据。

公开仓库变私有时暂停审查；权限撤销和卸载时取消任务、失效 Token 缓存并处理在途发布。

## 7.4 敏感数据与日志

模型调用前进行 Secret 扫描和占位符脱敏。不得向评论和日志写出完整 Token、私钥、凭证或连接串。

确定性扫描可能漏检，因此还需限制模型上下文、Artifact 权限、日志内容和输出传播。疑似 Secret Finding 引用位置与掩码，不附原值。

不默认把源码或仓库规则加入全局训练数据。模型供应商的数据处理条件需在选型时核实并对用户说明；平台本地不保存 Prompt 不等于供应商不留存。

## 7.5 保留与删除

| 数据 | 建议默认保留 |
| --- | --- |
| 安装信息、Memory、人工反馈 | 安装期间 |
| PR 与 Finding 元数据 | 12 个月 |
| 原始 Prompt/Response 与 Context | 30 天，可关闭 |
| Snapshot | 当前及有效 Replay 必要历史 |
| Evaluation Artifact | 90 天 |
| 审计事件 | 12 个月，脱敏 |

关闭原始输入保存会影响完整 Replay，界面必须说明降级。超过保留期的 Case 只保留统计或重新授权获取，不能无视用户删除要求。

删除流程停止新任务、撤销读取能力，清理在线数据库、向量、缓存和对象，再记录不含内容的删除凭据。首版目标为 24 小时内清理在线数据，受备份策略约束的数据在最长 30 天窗口内轮转删除；恢复备份时重放删除凭据，防止恢复已删除内容。

GitHub 已发布评论不属于平台数据库删除，操作前明确说明是否保留。安全审计保留最少元数据，不用审计名义保留已删除源码。

## 7.6 预算与配额

月度预算由 Review、验证、重试、备用模型、Embedding、Replay 与 Evolution 共同消耗。页面分别显示单次 Review 成本与全平台总成本，不能遗漏后台学习开销。

模型网关在调用前预留最大预算，在响应后按实际费用结算。并发任务共享事务或原子预算，失败预留过期释放。

月预算 80% 预警，100% 停止新自动任务；在途任务按已预留额度收尾。费用表记录价格版本与换算假设，不把人民币目标写成固定供应商承诺。

每月超过 ¥2,000 是允许的投入区间，不代表无上限。Beta 发布前配置明确全局硬上限与仓库配额。

## 7.7 限额与优化

默认跳过 Draft、大生成文件、Lockfile 与快照文件，支持维护者配置。连续 Push 合并为一次最新 SHA Review。

建议自动支持不超过 1,500 行变更的 PR；更大变更显示部分覆盖或要求手动触发。对仓库、安装和用户设置并发及频率上限，Fork PR 使用相同或更严格的数据约束。

按 SHA 和内容哈希复用分析；有效 Review 缓存包含 Pipeline、配置和 Memory 版本，避免规则变化后复用旧结果。生成与验证调用各有预算，不通过省略验证降低成本。

初期费用可参考模型 60%–70%、应用 Worker 约 15%、数据库存储监控约 10%、预留约 10%；具体以实际账单为准，不强求每个比例区间同时取上界。

# 第八部分：MVP 路线图、发布与竞争力

## 8.1 周期解释

4–6 周是接近全职投入、严格控制范围下的受控 Beta 计划。时间目标覆盖必要闭环与最小界面，不保证完整框架支持、全部可视化或统计显著的自进化效果。

10 仓库、100 PR 与四周留存属于上线后的验证目标，单独持续观察。进度不足时延后 P1 展示功能，保留验证、反馈、版本和预算边界。

## 8.2 六周交付计划

| 周 | 交付内容 | 验收 |
| --- | --- | --- |
| 第 1 周 | 项目骨架、CI、数据库、GitHub 安装、Webhook、任务、Check 与基础 Trace | 测试 PR 从事件到 Completed，重复事件不重复任务 |
| 第 2 周 | Model Gateway、Diff、Candidate、基本验证、摘要与行级评论、Review 页面 | 真 PR 出现 0–3 条有效锚定评论，成本可查 |
| 第 3 周 | 增量 Snapshot、JS/TS 符号与 Import、上下文检索、反证与过滤 Trace | 至少 20 个案例，展示上下文价值及 Trap 过滤 |
| 第 4 周 | Feedback、Memory 版本、Scope、人工纠错、后台 Replay/Shadow、自动激活与隔离 | 测试案例完成学习与回滚，不在真实仓库伪造独立反馈 |
| 第 5 周 | 约 50 个 Golden Case、版本对比、门禁、失败恢复、权限/删除/预算 | 输出固定版本评测报告，候选回归被门禁拦截 |
| 第 6 周 | Onboarding、状态体验、文档、Demo、配额、友好仓库试用 | 经验收的受控公开 Beta，公开已知限制 |

第 4 周演示可用人工构造数据验证状态机，但必须明确其来源；真实低活跃仓库保持 Shadow，不为演示加速激活。

## 8.3 拆分实施单元

完整设计是产品蓝图，实施分四个可验收单元：

1. GitHub、任务与数据基础。
2. Review 引擎与 Web 结果页面。
3. Memory、人工纠错与后台 Evaluation。
4. 安全、成本、回归与公开 Beta。

每个单元在开始编码前形成具体任务与验收计划。当前文档不包含已经执行的安装、部署或代码任务。

## 8.4 发布策略

先审查 ReviewPilot 自身，公开典型失败与纠正记录，再邀请 5 个友好 TS 仓库，验证安装、噪声、延迟与学习价值。

扩大到 10–20 个仓库时使用邀请码或允许名单、公开配额、Beta 标识和反馈入口。与维护者沟通并由其主动安装，不擅自在外部仓库发布 Review。

首批不依赖 Marketplace 审核，先提供 App 安装入口。Marketplace 资格与发布要求在实际提交前核实。

上线材料包括 README、架构、评测方法、Benchmark、贡献指南、安全政策、威胁模型、Roadmap、ADR、示例规则与本地开发说明。

开源许可需在公开发布前选择并核查依赖兼容性。工作默认倾向宽松许可，以减少贡献和试用摩擦，最终选择不影响本次设计文档交付。

## 8.5 可公开案例

制作两分钟演示：安装 → 真实 PR → Finding 证据 → 人工纠错 → 候选记忆 → Replay/Shadow → 自动生效/回滚。

发布版本报告，同时呈现误报、遗漏、成本与不支持的场景。对照试验使用相同 SHA、预算和数据，避免只挑对产品有利的样本。

Star 是传播信号；持续审查、维护者有效反馈和四周留存更直接体现产品价值。

## 8.6 对个人竞争力的产出

产品可以沉淀全栈交付、GitHub 集成、JS/TS 语义分析、可靠异步任务、AI 评测、自进化状态机、最小权限、数据隔离与成本治理经验。

优先记录以下可展示材料：

- 为什么选择模块化单体及何时拆服务。
- 一次误报如何被发现、定位和加入回归集。
- Memory 如何验证、自动生效与被人工纠正。
- 一次模型升级为何未通过门禁。
- 单次 Review 与后台进化成本如何分账及优化。
- 维护者使用数据与保留样本量的质量报告。

简历只引用实测结果，明确数据周期、仓库数量和指标口径。

# 附录 D：本次整理的澄清

1. 保留“自动进化 + 人工纠错”，普通 Memory 通过验证后自行生效。
2. 未回复与 Thread resolved 不直接作为正确标签；明确反馈与行为推断分开。
3. 启发式权重与校准概率分开，初期不把排序分展示为准确率。
4. Shadow 不自带真值，小样本保留观察状态。
5. 规则从可信已合并版本读取，外部 PR 不能自改审查标准。
6. Replay 固定历史时点，避免未来修复和生成证据泄露进验证集。
7. 自进化覆盖仓库记忆；平台级模型/Prompt 变更独立发版与评测。
8. Patch 是可选预览，第一版没有代码写权限。
9. 初期 50 Case 用于回归，不宣称代表全生态或统计显著提升。
10. 六周是 Beta 开发计划，真实用户增长与四周留存单独观察。
