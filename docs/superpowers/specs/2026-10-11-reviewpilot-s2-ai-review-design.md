# ReviewPilot S2 最小 AI 审查设计

日期：2026-10-11。状态：讨论方案已确认，书面设计待用户审阅。本文描述计划建设的能力，不表示 S2 已实现或通过验收。

S2 将 ReviewPilot 从连接检查推进到最小 AI 代码审查：读取公共 JavaScript 和 TypeScript 仓库的固定版本变更，生成少量候选，独立验证并核对真实代码证据，在中文 Web 中展示结果，最后由 Go 管理发布与对账。正常路径按 PR 串行处理，包含一轮候选生成与一轮独立验证；没有候选时不需要验证调用。

目标仍是实用的自进化代码审查产品，以及能体现 Go 后端、Web 全栈和 AI 应用工程能力的作品。S2 先建立可靠、可观察的审查基础；规则记忆、自进化与人工纠正不在本阶段提前实现。

## 阶段范围与批准边界

用户已确认先做 S2 本地开发与模拟验证，再进行真实接入。此决策仅放宽原计划的真实 GitHub 前置验收，不移除权限、预算、执行隔离与发布门禁。

本阶段交付范围包括固定 SHA 读取和 Diff 映射、模型网关、预算记录、受控串行工作流、证据门禁、Finding 存储、PR 结果页，以及 GitHub 发布适配和响应丢失对账。验收使用模拟模型与模拟 GitHub，不调用付费模型，不向真实 GitHub 写入。

现有 S1 已有 Go API、Outbox、RabbitMQ、Worker 内部 REST、租约和 epoch、结果持久化、连接 Check 与 Web 仓库管理。真实 GitHub 登录与安装、业务数据库切换、完整应用镜像运行和生产部署仍需外部验收，不能因 S2 模拟通过而标记完成。S1 当前事实以[迁移交付记录](../../reports/s1-go-migration.md)为准。

本设计补充[技术栈设计](2026-10-05-reviewpilot-tech-stack-design.md)，替代[原阶段计划](../../../2026-10-04-reviewpilot-implementation-plan.md)中 S2 的旧 TypeScript 后端路径与本轮进入条件。原[产品设计](2026-10-04-reviewpilot-design.md)的公共 JS/TS 范围、证据优先、低噪声、信任和数据处理约束继续有效。

书面设计获批后，另写具体实现计划，保存在 review-pilot 根目录。计划获批后才安装依赖或编写产品代码。实施只做 S2，完成后停止；不使用 subagent 或 worktree，仅做必要验证。代码注释为简洁英文，文档为中文，工程任务统一通过 Turbo 运行。

## 技术与组件职责

沿用 Go、Gin、GORM、PostgreSQL、RabbitMQ、事务 Outbox、Next.js、TanStack Query 和现有监控。新增 AI 能力在 TypeScript Worker 中使用 LangChain 模型适配与 LangGraph 固定节点工作流。不引入 BFF、gRPC、Python 服务、Redis、多 Agent 或对象存储。

| 组件 | S2 职责 | 禁止承担的职责 |
| --- | --- | --- |
| Go API | 授权读取、运行快照、阶段结果、预算事务、结果查询 | 模型自主规划与直接生成审查内容 |
| Go 调度与发布 | Outbox、执行权恢复、发布门禁、评论额度与远端对账 | 执行 PR 代码或绕过证据门禁 |
| Review Worker | 受限 Diff 分析、候选生成、独立验证、确定性过滤和排序 | 直连业务数据库、持有 GitHub 凭证或直接发布 |
| Web | PR 结果、证据、过滤原因、覆盖、费用和发布状态 | BFF、模型调用、数据库访问或凭证保管 |
| PostgreSQL | Go 管理的运行事实、阶段产物、预算和发布记录 | 代替 RabbitMQ 通知任务 |
| RabbitMQ | 版本化任务通知和确认 | 决定业务授权或最终结果 |

Worker 只持有自己的内部服务身份与模型供应商凭证。模型凭证从进程密钥配置读取，业务快照只包含配置版本与非敏感配置，不包含 API Key。浏览器不得获取供应商或 GitHub 凭证。

首个真实模型适配器选择 OpenAI-compatible，支持配置 baseURL、模型名和密钥引用，不固定供应商或具体模型。同时提供确定性 fake Provider，作为本阶段默认验收模式。LangChain 的 ChatOpenAI 支持自定义 baseURL，但不同兼容服务的结构化输出和用量能力仍需逐一核对。[ChatOpenAI 官方文档](https://docs.langchain.com/oss/javascript/integrations/chat/openai)。

本项目选择 Chat Completions、非流式调用，不启用供应商内置执行工具、远程 MCP 或自动 Responses API 路由。结构化输出方式由经过验证的配置指定，不能遇到不支持就偷偷改为自由文本、换模型或启动修复循环。SDK 隐式重试关闭，所有重试由模型网关显式管理。

模型服务地址只接受部署者配置的固定来源，不允许 PR 或普通用户指定任意 URL；真实模式要求 HTTPS，测试地址仅在隔离测试模式使用。供应商兼容性、数据处理条款与价格确认属于后续真实接入门禁，不靠一次模拟响应代替。

## 审查身份与固定上下文

Run 冻结 installationId、repositoryId、PR number、Base/Head SHA、Pipeline、Prompt、模型配置、价格和仓库配置版本。S2 使用独立的 review-v1 Pipeline；Memory 和可信规则版本明确为 none，不展示并不存在的规则命中。

S1 的 connection-check 与 foundation-v1 保留原语义，仍要求 modelConfigVersion 为 none。不能通过放松旧条件，把已有连接检查变成模型审查。S2 的 ai-review 使用独立任务和结果契约。

Go 获取 PR 元信息与变更清单，按固定 Base/Head SHA 读取内容，并在获取动态 PR Diff 前后核对当前版本。如果无法确认 Diff 与快照一致，标记 Stale 或覆盖不足，不把最新 Diff 拼接到旧 SHA。Worker 只能通过当前任务的受鉴权内部 REST 读取该仓库、该快照内的数据。

每份实际读取结果记录路径、SHA、内容哈希、读取状态和大小。路径不得越界，不能跟随仓库外链接；绝对 URL 不作为代码读取入口。分页不全、二进制、删除文件、重命名、缺失 patch、CRLF 和末尾无换行均有明确结果，不统一伪装成空文件。

默认自动覆盖上限为 1,500 行新增与删除变更。文件数、单文件字节、总字节、读取超时、输入 Token 和输出 Token 必须有经校验的有限配置；超过任一限制记录实际读取范围与跳过原因。大 PR 可以部分审查，但不能声称覆盖全部代码。选择范围的顺序固定且可复现，不交给模型随意扩张。

最小上下文包含选中的 Diff、固定版本的相邻代码，以及判断候选是否由本次变更引入所需的 Base 内容。S2 不实现完整 AST、跨文件调用图、全仓检索或向量化；缺少必要上下文时放弃对应候选，不以猜测补齐。安全与业务背景不足仍可能造成漏报，Web 要显示这项覆盖限制。

## 串行审查流程

LangGraph 用于代码预定义的阶段顺序和有限分支，不让模型动态挑选工具或决定无限循环。[LangGraph 工作流官方说明](https://docs.langchain.com/oss/javascript/langgraph/workflows-agents)。

正常流程为：

1. Go 领取并校验执行权，Worker 启动持续续租，读取固定上下文及已完成的匹配阶段结果。
2. 解析 Diff，记录可用锚点、实际覆盖和读取限制，脱敏后生成模型输入。
3. 通过模型网关预留预算，进行一次候选生成，并保存合法的候选阶段结果。
4. 候选先通过基础引用校验；没有可验证候选时跳过验证调用。
5. 独立验证使用新的请求，以候选声明和原始证据的脱敏视图为输入，检查失败前提、Base/Head 归因、已有保护和反例，不复用生成阶段的对话历史，也不跳过脱敏。
6. 确定性核验、去重和排序，保存最终 Findings、过滤原因、覆盖和用量；Go 接受结果后，Worker 才确认消息。
7. Go 根据最新权限、SHA、评论额度和远端事实建立并执行发布计划。模拟模式只写模拟服务。

生成与验证可以使用同一个配置模型，但请求与 Prompt 分离。这里的独立验证是流程隔离，不是独立专家，也不能保证没有共同误判。两个阶段均通过 Schema 和确定性校验，仍不等于问题正确。

候选包含标题、严重程度、问题类别、失败条件、影响、是否本次引入或加剧、证据引用和建议验证方法。验证结果包含支持或拒绝、结构化理由与对应引用，不采集隐藏思维链。建议验证仅供维护者执行，本阶段不会安装依赖、运行 PR 测试或验证脚本。

候选数、引用数、字符串长度与阶段结果总大小均受 Schema 和内部 API 限制。不在无法验证的截断结果上继续发布。

## 证据门禁与低噪声策略

模型不能创建证据事实。引用只能指向 Go 提供的实际读取记录，确定性检查核对租户、仓库、路径、SHA、行范围、内容哈希及引用片段。跨仓库证据属于隔离异常，终止 Run；普通错误行号或缺失证据过滤对应候选。

可发布 Finding 必须满足：

- 失败条件、影响与建议验证具体，不是泛泛风格建议。
- 生成与独立验证均通过合法 Schema，且结论得到真实代码引用支持。
- 有本次引入或加剧的依据；Base 内容缺失、仅发现历史问题或无法归因时不发布。
- 已读取范围内未发现明确反证或已有保护；必要上下文缺失时执行 Abstain。
- 与已有发布根因不同，并满足确定性发布位置或摘要条件。

确定性检查能够证明引用来自读取内容，不能仅凭字符串存在证明完整符号解析、运行时调用链或业务影响。S2 对不存在的代码引用必须拒绝；对无法确认的函数关系或业务假设不得表述为已证实。

过滤使用稳定原因码，例如 INVALID_REFERENCE、INSUFFICIENT_CONTEXT、NOT_INTRODUCED、EXISTING_PROTECTION、DUPLICATE_ROOT_CAUSE 和 COMMENT_LIMIT。Web 展示原因与引用，不展示模型隐藏推理或未经脱敏的原始响应。

根因指纹由 Go 按版本化规则生成，包含问题类别、规范化路径、稳定代码锚点与失败条件结构；不直接采用模型给出的哈希或标题。身份范围为同一安装、仓库和 PR，跨 Run 去重，行号移动本身不产生新根因。语义去重仍有边界，不声称能识别所有改写与重命名。

同一 PR 默认最多发布 3 个不同根因，累计计算，不随新 SHA 或新 Run 重置。行级评论与摘要中列出的 Finding 共用额度，同一问题不能在两处重复计入。已经发布的评论被删除或标记解决，不自动释放额度或触发重发。超过额度的已验证问题留在 Web，标记未发布原因。

没有通过候选可以正常结束，但文案是“本次覆盖内未发现可发布问题”，不是“代码没有问题”。内部排序分只显示可信等级，不转换成准确率百分比。

## 模型预算与未知用量

Go 原子管理单 Run 限额、仓库每日配额及全局月度上限。候选生成、验证和显式重试使用同一预算账本，按 purpose 分账；后续 Evolution 可复用协议，但 S2 不产生学习费用。

每次网络调用都有独立 callId 与 reservationId，冻结模型和价格版本、币种、最大输入及输出量。金额使用整数微单位，不用浮点累加；跨币种汇总必须冻结换算口径，未配置时不混加。fake 用量与测试价格明确标记，不能混入真实账单或产品成本指标。

真实调用必须配置有效价格、有限输出与调用次数、Run 限额、仓库配额和全局上限。无法计算保守预留、供应商具有未纳入价格的收费项或缺少必要配置时，拒绝调用。应用预留是基于冻结价格的费用控制，不承诺供应商账单永远与估算一致。

模型调用事实区分 reserved、dispatching、settled、released 和 uncertain。Worker 发出请求前，先通过 Go 持久化 dispatching；响应后提交用量和响应摘要哈希，再保存对应阶段产物。已发送的状态用于阻止另一执行者自动重发同一调用，不宣称已经实现外部请求恰好一次。

可信用量可以结算并释放剩余预留；明确未发送的调用可以释放。超时、进程崩溃、响应丢失或缺少用量字段时，保留预留并标记 uncertain，不能仅因租约或 TTL 到期释放。合法内容但用量未知时仍暂停后续高成本阶段与发布，等待对账，不把运行记成已完成。

同一调用状态的重复提交幂等处理，内容冲突拒绝。旧 Worker 失去租约后不能改业务结果；迟到用量也不得绕过 fencing 覆盖记录，交由授权对账处理。

每个模型阶段至多允许一次显式重试，且重试前重新预留。只有明确允许重试、费用已结算或确认未发送的失败才自动重试。无效 Schema、未知发送结果和凭证错误不进入自动修复循环；不配置静默备用模型。底层 SDK 不得额外重试。

全局月度预算达到 80% 提示，100% 停止新增自动调用；已预留调用可以按预留收尾，未预留的验证不能跳过预算检查。仓库每日计费周期使用 UTC，并明确显示重置时间。实际费用超过预留时记录差额、阻断后续调用并提示对账，不能截断费用为预留值。

未知用量由部署者核对供应商记录并留审计凭据；本阶段不自动抓取供应商账单，也不新增完整人工计费后台。无法确认收费时继续保守占用额度；明确批准重新调用也必须使用新 callId、新预留，并保留前一笔未知成本。

## 执行恢复与状态表达

沿用 S1 的数据库时间、租约 token、runtime mode 和 execution epoch。Worker 持续续租，而不是只在模型调用前续租一次；失去执行权时取消本地可取消请求并停止读取、预算申请和结果提交。取消不等于供应商一定停止计费，未知调用仍需对账。

阶段产物由 Go 经内部 REST 保存到 PostgreSQL，不给 Worker 添加检查点数据库角色。S2 不使用 LangGraph 原生持久化来替代业务状态；重启后由受控流程读取已完成阶段，后续完整检查点与 Replay 在 S3 再扩展。

恢复键包含 Run、快照输入哈希、阶段、上下文哈希、Pipeline、Prompt 与模型配置版本。原始 Run 输入哈希沿用 Go 对持久化快照的计算，不由 TS 重新序列化后猜测。同一键的结果不可变，旧租约不能写入；版本或内容不匹配不能复用。

只恢复已完整提交的阶段。模型已响应但阶段结果尚未保存就崩溃，仍可能无法恢复该调用结果；默认进入待对账，不自动再花钱生成。完整阶段结果恢复与模型请求幂等是不同问题。

| 条件 | Run 和处理结果 |
| --- | --- |
| 正常执行 | Queued → Indexing → Reviewing → Verifying → Publishing，按实际阶段推进 |
| 完整覆盖且结果与发布已确定 | Completed；零候选或没有剩余评论额度同样可以完成 |
| 范围超限、文件不可读等导致覆盖不足 | Partial，并保留已完成结果和跳过原因 |
| 当前 Head 不再匹配 | Stale，停止旧结果发布 |
| 撤销授权、私有化或仓库停用 | Cancelled，停止读取与发布 |
| 无法恢复的服务、Schema 或配置错误 | Failed，展示安全的稳定错误码 |
| 调用或发布事实未知 | 保持当前阶段，附 needsReconciliation 和阻断原因，不自动重调度或显示成功 |

不为每类阻断增加新的 Run 枚举。needsReconciliation 是持久化的恢复事实，调度扫描必须显式排除，不能仅依赖页面标签。待对账事实提交并确认后才 ack，保留逻辑任务供授权对账恢复，不无限 requeue。零候选路径可跳过 Verifying 和 Publishing；Partial 最终状态在允许的发布与对账结束后确定。

Go 原子接受最终审查结果、写 Findings 与过滤记录、更新任务及建立待发布事实。Worker 提交响应丢失时先确认已接受结果，再 ack；重复通知不得重新调用模型。结果接受不等于发布完成，发布保持独立租约与重试治理。

## REST 契约与持久化扩展

契约源仍在 packages/contracts，由 OpenAPI 与 JSON Schema 生成 Go 和 TS 类型，并做运行时校验。S1 消息 v1 保持不变；新增 v2 消息表达 ai-review，Worker 显式区分 v1 连接任务与 v2 审查任务，未知版本隔离。上线顺序必须先具备 v2 消费能力，再允许 Go 投递 v2，不能让旧 Worker 把新任务隔离后仍声称正常运行。

新增内部能力限定于当前任务和有效租约：读取审查上下文、预留及记录模型调用、提交与读取阶段产物、提交最终 Review 结果、确认已接受结果。确认接口只能返回匹配身份与哈希的事实，不能借此获得其他任务或源码。Worker 无任意仓库浏览或通用数据库查询接口。

外部 REST 提供授权仓库的 PR 与 Run 查询、Findings、过滤原因、覆盖、发布及费用摘要。浏览器同源直连 Go，沿用会话与当前维护权；变更能力遵守 Origin、CSRF 与预期配置版本。仓库安装身份必须包含在访问范围内，不能只凭 repositoryId 或 runId 授权。

具体端点、DTO、大小上限和生成任务由书面实现计划列出，实施前加入契约源，生成文件不手工编辑。逻辑数据包含模型调用与预算账本、阶段产物、证据清单、Findings、过滤记录、覆盖和根因发布事实，不把模型自由 JSON 当成可直接写库的业务实体。

新增 SQL 从 0004 开始，保留 0001–0003 内容与迁移哈希，不使用 AutoMigrate。扩展现有结果与发布事实而不是建立互不对账的第二条发布通道；新增大小和状态约束只作用于匹配任务类型。

S2 默认关闭真实 AI 触发与真实发布。fake 模式只允许使用明确的测试数据和模拟 GitHub 地址；真实配置中缺少任一必要条件必须拒绝，而不是退回 fake 后给真实用户输出模拟结论。模型模式、GitHub 模式和 Run provenance 均由服务端记录。

## GitHub 发布与远端对账

GitHub 读取和写入由 Go 执行。真实接入需要 Contents Read、Pull requests Write、Checks Write 和必要 Metadata；创建 PR Review 需要 Pull requests 写权限，不能把 S1 Check 权限视为已满足 S2 发布。[GitHub PR Review 官方接口](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request)。本轮不实际修改 App 权限或安装。

发布只使用 COMMENT，不自动 APPROVE 或 REQUEST_CHANGES。Review 绑定快照 Head SHA，内容包含具体问题、证据与验证建议；代码片段最小化并再次脱敏，不将候选、未知结论或隐藏推理塞入摘要。

Go 在同一 PR 范围内原子预留根因与评论额度，写入不可变发布计划、计划哈希和稳定远端标识，再调用 GitHub。合法新侧变更位置优先行级评论；没有可用行级锚点但仍有充分固定版本证据时转摘要，同样占用一个问题额度。无问题不额外创建“无问题”讨论评论，可通过 Check 和 Web 展示结束状态。

发布前重新验证安装、公开状态、启用状态、PR Head 与计划快照。发布后再次核对版本；若期间变更则标记 Stale，并保留真实远端事实，不声称已经消除 GitHub 与数据库之间的竞态。

每次发布记录 Review、Comment 和 Check 的远端 ID、根因、Head、作者 App 身份与计划标识。响应丢失时先分页查询并按这些事实对账；普通用户复制的标记不能冒充本 App 发布。已发现的写入只补记本地，不重复发评论。

尚未确定是否成功的写入保留评论额度，并进入待对账，不因为一次查询未找到就立即重发。明确未写入的可重试失败使用有界退避并遵守限流提示；不能自动改锚点、改内容或拆分请求以绕过对账。跨远端 API 和 PostgreSQL 不承诺 exactly-once。

模拟 GitHub 必须能够表达真实成功、明确失败、成功后响应丢失、分页、SHA 改变和授权失效，不能只有始终成功的实现。模拟生成的远端 ID 和链接与真实事实区分。

## Web 结果与可观测性

在现有仓库管理中增加 PR 列表或 Run 入口，打开对应 PR 的审查页；不重做独立门户或重设计全部导航。用户可以切换历史 Run，但默认展示当前版本，旧 SHA 明确标记。

页面至少展示：

- PR 标题、Base/Head、Run 状态、Pipeline 与模型配置版本，以及模拟或真实模式。
- 已验证 Finding 的失败条件、影响、最小证据片段、建议验证与发布状态。
- 已过滤候选及安全的理由，区分未验证、主动放弃和评论额度不足。
- 已读与跳过的文件和变更范围、缺失 patch、超限原因，不以单个百分比替代覆盖说明。
- 调用次数、可用 Token 用量、按用途的费用、未结算预留、币种和价格版本。
- 失败、Stale、Cancelled 与待对账原因，避免无限显示“正在审查”。

S2 不增加“有用”“误报”“创建规则”或自动修复的假按钮，不展示未实现的 Memory 页签、Replay 对比或准确率卡片。人工纠错与自进化的交互和持久化在 S4 实现。

采用现有 TanStack Query 与直接 Go REST，按状态有限轮询，最终状态停止常规高频刷新；错误响应包含 requestId 和稳定错误码。鉴权、源码引用和费用详情由 Go 检查，页面可见不等于任意 API 可读。

新增模型调用数、阶段耗时、超时、拒绝原因、Token、估算费用与未知调用等必要指标。runId 和 PR number 放入业务记录或受控日志，不作为无限增长的指标标签。没有真实调用时不生成真实费用或质量指标。

业务阶段记录包含版本、结构化决策与证据引用，不依赖被采样的监控 Trace。日志和 OTel 不写完整源码、Prompt、原始模型响应、密钥或隐藏思维链；模型错误先映射成安全错误码。监控故障不得阻断审查。

## 安全与数据保留

PR 代码、注释、描述、文件名和规则文件改动均为不可信数据，不能覆盖系统指令、预算、权限或工具边界。S2 不启用仓库规则导入，外部 PR 不能让自己的规则修改直接豁免自身审查。

模型上下文发送前做密钥脱敏；保存引用到原始内容的哈希和行映射，脱敏片段不能被错误当作未经修改的源码证据。进入页面和 GitHub 发布的内容再次检查。脱敏不是绝对防泄漏保证，真实接入仍需最小输入与供应商数据处理确认。

PR 代码只静态读取，不执行安装脚本、插件、测试、服务或原生扩展。Review Worker 服务身份无 Evolution 权限，也不能提交规则激活或改变仓库配置。

原始 Prompt 与模型 Response 默认不持久化；必要的脱敏上下文和带片段阶段产物最多保留 30 天，保留关闭时仅保存必要元数据与哈希，无法恢复的阶段明确降级。PR、Finding 元数据和最小审计沿用 12 个月政策，持久化源码片段不得借元数据名义延长保存。

产物有归属、大小与到期时间，读取校验授权；到期清理与查询过滤同时生效。产物被清理后不能假装支持完整恢复或 Replay。停用与撤销停止新读取；删除流程必须覆盖新增调用、产物和 Finding 内容，不能遗漏 S2 表。完整备份删除与恢复防回流验收继续作为真实部署门禁。

公开仓库不意味着可以无控制地把全部代码发送给第三方。S2 模拟验收只使用明确的合成或许可 Fixture；真实调用时由操作者确认供应商、允许的数据范围和费用配置。

## 必要验证与阶段验收

采用少量确定性 Golden Fixture，模型响应脚本化，用来验证流程、引用、过滤和失败恢复，不据此报告真实模型精度。至少包含可发布问题、零候选、错误引用、非本次引入或已有保护、重复根因，以及上下文不足。

定向验证覆盖 Diff 新增删除重命名、CRLF、缺失 patch 和分页；Schema、脱敏、调用上限与未知用量；预算并发争抢；失效租约与阶段恢复；同 PR 跨 Run 去重、共享评论额度、Head 变化、权限撤销，以及远端成功后响应丢失。

最后执行一条隔离全链路：模拟 Webhook → Go 固定快照及 Outbox → RabbitMQ → Worker fake 生成与验证 → Go 保存结果 → 模拟 GitHub 发布与对账 → Web 查询可展示的数据。保留关键观测证据，不扩展全面浏览器矩阵、压力测试或多模型评测。

本阶段可以判定本地模拟验收通过的条件是：受影响包构建和静态检查通过，关键案例满足预期，完整流程与阻断状态可查看，费用不漏记已知重试、未知费用不释放，旧执行者与旧 SHA 不能发布，重复事件和响应丢失不重复产生已确定的评论。

真实接入仍需独立批准与验证：

1. 真实 S1 App 登录、安装、启用、PR 和 neutral Check，以及专用环境 Go 模式切换与旧消费者停止。
2. S2 App 最小权限、供应商能力、数据处理与价格配置。
3. 专用公共 PR 的真实模型输出、实际费用、证据和 0–3 条真实发布。
4. 完整镜像与入口运行、手工页面可用性及生产运维事项。

未完成这些事项时，交付结论只能是“S2 本地实现与模拟验收通过”，不能写“真实 AI 审查上线”。真实精度、漏报、延迟和成本目标需要独立人工标签与实际账单，不用 fake 数值替代。

## 后续阶段与当前停止点

S3 扩展固定版本上下文、JS/TS 分析、反证、完整阶段恢复和开发案例；S4 增加人工纠错、版本化规则记忆、候选学习、Replay、Shadow、自动激活与回滚；S5 形成可靠评测；S6 进行受控 Beta。
